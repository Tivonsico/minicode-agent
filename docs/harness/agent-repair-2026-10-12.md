## 已复现的问题

### 管道掩盖失败退出码

在真实操作系统沙箱中运行 `python3 -c "raise RuntimeError('REPRODUCED_FAILURE')" 2>&1 | tail -2`，Python 抛出异常，Shell 却返回 `exit_code=0`。工具记录为 `succeeded`，后续验证也可能被记成 passed。

证据：`others/test_record/diagnostics/pipeline-before.json`。这是运行器对进程退出状态的处理缺陷，不能靠判断日志里是否出现 Traceback 来补救，合法测试也可能包含预期异常。

### 执行完成与验证证据缺少结束前核对

修改前的循环收到无工具调用的 stop 响应后直接结束，没有核对验证是否发生在最后一次文件修改之后。即便早先测试通过，之后再修改代码，也可能沿用旧验证结果。

上一轮的 `sympy__sympy-19487` 还暴露了另一种错误：Agent 自增测试确认了错误实现，没有覆盖需求中的未知假设。修复验证流程需要区分需求复现与旧行为回归，避免只测试自己已经写出来的行为。

## 具体修改与取舍

### 进程退出码

`backend/execution/codex.py` 对标准 sh/dash 配置采用无用户启动脚本的 Bash，开启 pipefail；Bash/zsh/ksh 也启用该选项。保留原始命令，不按日志关键词推测成功与否。原探针修复后返回 failed、exit_code=1，证据保存在 `others/test_record/diagnostics/pipeline-after.json`。

这能修复管道最后一个命令掩盖上游失败的问题。它不能阻止显式的 `|| true`，也不是判断测试质量的工具。本机验证范围是 macOS 的 POSIX Shell，没有声称完成 Windows 的等价验证。

### 完成前核对

新增 `backend/runtime/verification.py`，只投影当前轮的真实日志。发生成功的 WriteFile、EditFile 或 DeleteFile 后，最后一条执行验证必须晚于最后一次文件修改，并且状态为 passed。旧轮证据、先测试后修改、通过之后再失败，都不能被用来确认本轮过程验证。

`backend/runtime/loop.py` 在模型请求结束时调用这项核对。缺失、过期或失败时，将系统反馈加入下一次已记录的模型输入，最多反馈两次，仍未补齐则暂停并保存现场。反馈不会伪装成用户消息，不自动重放工具副作用，模型请求仍计入原本的 30 次预算。

核对事件带有 run、turn、step、request、message 关联，以及最后修改与验证的日志序号。普通会话的前端轨迹增加“完成前核对”记录。新的核对代码与进程策略加入模式权限版本摘要；SWE-bench 报告同时记录 backend_code_digest。

核对范围明确为文件工具的变更。当前没有对任意 Shell 命令做文件系统差异审计，也不能证明 passed 的测试覆盖了全部需求；正式编码成绩仍由独立 Docker 验收判定。无可用验证沙箱时不强制发起不可执行的 Shell。

### 短期状态与检查点

`backend/runtime/session.py` 在成功修改文件后，将已经执行过的验证状态置为 stale；失败的修改不会使证据失效。短期状态与随后生成的检查点不再继续展示此前的 passed。完成核对读取原始事件，而不是信任可手动编辑的状态字段。

### 需求契约与预算

固定系统指令要求从需求与现有接口列验收条件，复现问题，再检查修复与必要回归；不得为实现方便增加隐式假设、缩小输入范围，或者用默认值掩盖原来的错误。到第 24 次请求后提示剩余预算，避免临近上限仍扩展无关任务。本轮没有提高请求上限。

第一次复测后，速度推导题仍把未定义的速度当作零，说明新鲜的过程证据无法阻止错误预期。因此补充了一次通用契约复核：模型首次给出带有效验证的结束响应后，再请求它检查新增默认值、隐式假设、输入范围和原有异常。它可以据此修改代码，但修改后必须重新验证。

契约复核每轮最多请求一次，使用同一个模型，并正常记录请求与用量。这不是独立评审模型或隐藏测试判分器，不能把“已请求复核”写成“已独立验收”。事件以 review_requested 标识这个阶段。
