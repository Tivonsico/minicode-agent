# 四种执行模式

同一套 Agent Loop 使用四种固定权限策略。模式是执行权限与上下文身份，思考强度是模型推理参数，二者独立。新会话默认 Manual；模式保存在会话日志的 `mode_selected` 中，重启后恢复；执行中禁止切换。补充指令属于应用共享设置，修改后下一轮生效。

| 模式 | ReadFile / Glob / Grep / 技能资料 | WriteFile / EditFile | DeleteFile | Shell |
| --- | --- | --- | --- | --- |
| Manual | 自动允许 | 逐项确认 | 逐项确认 | 逐项确认 |
| Accept Edit | 自动允许 | 自动允许 | 逐项确认 | 逐项确认 |
| Plan | 自动允许 | 禁止 | 禁止 | 禁止 |
| Auto | 自动允许 | 自动允许 | 自动允许 | 自动允许 |

## 取舍与实现边界

参考 [Claude Code 官方模式说明](https://code.claude.com/docs/en/permission-modes)的交互分工。本项目采用确定性的 allow / ask / deny 权限表，不新增 LLM 安全分类器，避免增加延迟、成本与另一个不确定判定环节。四个模式共用生命周期、上下文构造、工具校验和沙箱，不复制四套循环。

Plan 不开放 Shell。当前 Shell 接受任意命令文本，正则规则无法证明一个允许的命令完全只读，因此 Plan 通过文件读取、搜索及技能资料工具进行分析。所有禁止工具既从 schema 中移除，也在实际 dispatch 前检查；模型伪造调用不能绕过。Plan 的 completed 只表示本轮规划结束，不能代表实现完成或测试通过。

Accept Edit 自动批准写入与编辑，删除和命令仍确认。Shell 能在沙箱工作区内删除与改写文件，因此 Auto 并不是仅放宽编辑次数；它允许自动执行有副作用的工作区命令。采用原有危险命令检查、路径及密钥保护、读版本冲突检查、操作系统沙箱、网络关闭及无沙箱拒绝执行。正则拒绝是补充防线，不能单独证明抵御所有提示词注入。

固定权限在 `backend/modes/catalog.py`，执行决策在 `backend/permissions/policy.py`。前端「权限与指令」展示完整权限表、安全边界、固定模式指令与版本；只允许编辑每模式最多 4000 字符的补充指令，保存在 `.minicode/modes/settings.json`。接口禁止额外权限字段，使用 revision 防止覆盖别人刚保存的版本。项目提示词、全局提示词、技能和记忆均不能修改程序固定权限。

## 可核对的身份

每次启动运行，RuntimeSession 深拷贝模式配置，并固定以下字段：

- `agent_mode`：manual / accept_edit / plan / auto，表明执行身份。
- `mode_policy_version`：SHA-256，覆盖固定权限、边界说明及执行/路径/命令等守卫代码。它与 benchmark 的完整 harness_digest 作用不同。
- `mode_prompt_version`：SHA-256，覆盖共享运行时指令、本模式固定指令和实际补充指令。系统/项目/记忆等完整模型输入仍由既有 input_versions 及脱敏请求快照核对。

身份通过已有 run / turn 作用域继承到 step、请求及重试、工具调用、审批请求/结果、运行结束、后台记忆请求和实际输入快照。审批决议来自另一个 HTTP 请求，因此显式复制原票据身份。进程退出后的恢复记录复制原始身份，不重新执行工具。

Short Memory 与 Checkpoint 保存原任务的三个字段；手动同步时即使已经切换下一轮模式，也保留原任务身份。短期状态编辑不开放身份字段。压缩记录额外保存 source_modes 和每轮 source_profiles，混合模式历史有明确来源。下一轮始终重新构造当前固定系统规则，压缩摘要不能获得执行权限。

长期记忆按项目共享，不复制成四套互不相通的知识库；记忆条目保存原消息的模式版本、run 与 turn。跨模式可复用显式项目约定，但引用只是资料。后台提取继承旧作用域，后续新轮切换模式不会改变它的来源。人工编辑保留原始来源；人工新增条目标记当时选择的模式。旧日志缺少身份时保留 null，UI 显示「历史未标记」，不猜测或回填 Auto。

## 评测与历史导入

`Case.mode` 仍表示 task / history（运行任务 / 历史规则），`agent_mode` 表示执行身份。新建 benchmark 使用 `agent_modes` 选择矩阵，`goal` 区分 implementation / planning。

原有 `data/tasks.json` 的 30 项编码任务和 114 条验收条件不变；新增 `data/planning.json` 的 4 项规划任务，覆盖边界修复、输入校验、多轮约束、含恶意指令的项目文件。任务包升级至版本 3，保留用户改过的任务和旧报告。默认选中原有 30 项编码任务，以 Auto 执行；规划任务需要显式选择 Plan。

- implementation 在 Manual / Accept Edit / Auto 中分别运行，文件、函数返回值、异常、回归和安全条件由原独立验收器判定。
- 用户添加工作目录时原有管理流程会初始化项目提示词和技能目录；规划验收在这一步之后建立文件基线，也检查运行时已准备的项目提示词不能变化。
- planning 只在 Plan 中运行，使用独立规划关键词、文件约束、工作区文件不变及不尝试写入/命令检查。关键词只是内容覆盖检查，不代表高质量计划。输出关键词不放入模型上下文。
- 每个「题目 × 兼容模式 × 重复」使用独立临时工作区与会话，并在实验开始时冻结模式配置和全局补充提示词。没有兼容目标的选择在执行前拒绝，不悄悄跳过整类任务。
- Manual / Accept Edit 的待审批操作由明确的 approve / reject 脚本模拟用户，写入 options 与 environment；只有临时工作区，不是真实人工确认数据，仍不能覆盖硬拒绝。
- 报告保存每次模式身份、目标、审批次数，以及 mode_metrics / goal_metrics。task_success_rate 只计算实现目标，planning_success_rate 单列；总体验收与耗时混合统计不用于声称编码能力。重复至少一次成功按 case_id + agent_mode 分组。
- 历史会话导入保留多种模式及各消息版本，可按来源模式筛选规则；检查与导出不调用模型或工具。旧报告保持原样，缺失模式按 legacy_unknown 展示。新增模式后的质量成绩必须重新实测，旧 83.3% / 96.7% 不属于新模式矩阵成绩。

## 验证文件

`others/test/integration/test_modes.py` 检查实际权限执行、伪造调用、固定边界、运行中冻结与版本冲突、审批关联、取消与恢复、异步记忆来源、混合模式导入、矩阵隔离、拒绝审批、规划验收及 Auto 的旧读取版本拒绝。这些是工程正确性测试，使用脚本模型响应；不能冒充真实模型的 benchmark 成绩。
