# 运行证据、检查点与历史评测

后续更新（2026-10-19）：独立 ShortMemory 已合并到 checkpoint，启动支持快照加后缀恢复。当前协议见 [检查点恢复](../checkpoint-recovery.md)；下文保留此前实现与验证记录。

本次实现围绕一个判断：Agent 的可展示能力不仅是生成代码，还包括解释“当时看到了什么、实际做了什么、在哪一步结束、哪些结果经过验证”。先让这些事实可关联、可查看、可评测，再扩展可靠续跑。

## 发现的问题 → 设计判断 → 实现 → 验证 → 边界

| 发现的问题 | 设计判断与实现 | 为什么有价值 | 验证与边界 |
| --- | --- | --- | --- |
| 原有 journal、短期状态和压缩缓存已存在，但 `run_id` 没有贯穿；辅助请求和审批决定容易丢失来源 | 使用任务局部的不可变关联上下文，连接 session、run、turn、step、request、message、call、approval。后台记忆保留来源 run/turn，并通过 `source_step_id` 指向触发步骤 | 可以从一条审批或辅助请求反查用户输入和上游请求；避免下一轮开始后把后台结果错算到新任务 | 测试覆盖审批关联和两轮重叠的记忆提取。工具的 `call_id` 来自供应商，定位时应结合 session/request，不把它当作全局唯一编号 |
| 只有“请求开始”或“有输出”不能解释失败和重试 | 每个实际模型尝试有独立 `request_id` 和结束状态；记录首输出、首正文、总耗时。run、step、tool 和 approval 也闭合；启动恢复补记中断 | 可以区分等待模型、生成过程、工具执行与审批等待，不靠最终回复猜原因 | 覆盖真实 HTTP 模拟重试、输出后断流、取消、审批拒绝、进程退出。恢复不重跑工具；未知副作用仍要求核对 |
| 对话消息不等于发给模型的真实输入 | Provider 与记录器共享请求构造函数；脱敏后保存实际 messages、tools、模型参数及 instructions/tools/payload 内容哈希 | 压缩、提示词、工具定义发生变化后，仍能解释模型当时看到的上下文。内容哈希是版本指纹，不是假设用户维护了人工版本号 | 覆盖输入内容、哈希、已知密钥脱敏与路径限制。历史请求没有存过的输入无法补造；脱敏针对已知密钥和常见凭证格式，并非任意敏感信息自动识别 |
| “完成”会被误读成“验证成功” | `turn_end/run_end` 记录执行结束；带 `purpose=verification` 的 Shell 记录实际验证结果；独立报告按冻结规则检查历史事实 | 把模型的自述和外部执行证据拆开，可以讨论完成率与验证覆盖的差别 | 同一轮完成任务在普通规则下通过，在要求验证时失败。Shell 验证代表命令退出结果，不证明测试质量；目前报告是历史规则验收，尚非隔离环境中的隐藏测试验收 |
| 日志散落，状态缓存不好查看，评测结果难复核 | 前端增加运行记录六个页签和独立评测页。检查点保存当前 ShortMemory，人工更新带来源与版本检查；报告保存规则版本与样本截止 seq | 可以现场展示一条任务的证据链，也能控制人工操作与自动状态更新之间的冲突 | API 和浏览器验证查看、同步、状态编辑、记忆编辑、报告生成及下载。导出和历史评测不派发模型或工具 |

## ID 的具体含义

- `session_id`：会话容器，多次输入共享一个会话。
- `run_id`：一次执行任务的身份。用户再次输入或“继续”会开启新的 run。
- `turn_id`：这次用户输入及由它触发的消息、工具结果。当前正常执行时一个 run 对应一个 turn，保留两个概念便于后续恢复建模。
- `step_id`：主循环的一次上下文准备、模型请求和工具批次。
- `request_id`：一次实际请求尝试。重试产生新 ID，而同一输入可以共用输入文件；摘要和记忆请求也记录各自用途。
- `message_id`：用户或助手的完整消息。流式片段共用助手消息 ID。
- `call_id`：模型指定的工具调用 ID。结果通过相同 ID 与请求来源关联，而不是另造一个无法匹配的“结果 ID”。
- `approval_id`：审批票据，从请求、决定到关闭贯穿。前端提交决定时仍保留来源 run/turn/step/request/call。
- `seq`：会话 journal 的单调序号，定位每条事件、分页和确定报告样本边界。

后台记忆不假装仍在执行原步骤：`step_id` 为空，`source_step_id` 保留触发步骤；run、turn 不变。历史日志缺失的关联和耗时保留未知，不回填虚构事实。

## 前端操作

打开工作区详情，点击“查看运行记录”。

1. **时间线**：查看每轮输入、模型和辅助请求、步骤、工具结束、审批、压缩、验证和运行结束。
2. **日志**：按事件类型筛选、分页展开；请求记录可以查看脱敏后的实际请求输入。
3. **摘要历史**：查看每次压缩的时间、来源日志范围和压缩后保留的历史。没有达到上下文阈值就没有摘要，不为展示而额外调用模型。
4. **检查点**：查看自动与人工快照；“同步当前状态”立即追加一份当前 ShortMemory 快照。执行中的任务保存为 `running`。
5. **短期状态**：更新目标、下一步、备注和任务标记，保留人工来源。版本冲突时要求刷新；任务执行中不能人工标为完成，空闲时不能伪造运行中。目标和备注不改写对话消息，也不意味着向当前在途请求注入新指令。
6. **长期记忆**：按当前项目或全部项目查看，添加、编辑、删除。编辑采用版本检查，并阻止早已开始的旧提取覆盖用户刚修改的内容。无工作目录时使用无项目范围。

侧栏“评测”进入会话之外的页面。可增加、修改、移除规则，选择已结束会话，生成并导出报告。运行中的会话不能纳入报告。初始提供一个问候规则作为格式示例，不把它包装成完整 coding benchmark。

规则支持：用户输入匹配、最终回复包含、工具成功执行、禁止工具调用、执行状态以及是否存在实际通过的验证记录。报告冻结评测集及其版本、样本 `covered_seq` 和逐项判定；再次修改规则不会改写旧报告。

指标包括规则通过率、规则覆盖率、样本数量、耗时 P50/P95、首正文 P50、请求和重试次数、工具失败、失败分类、已知 tokens 和用量未知请求。费用没有价格及完整用量来源，保持未知。延迟指标覆盖所选会话的运行记录，通过率针对匹配规则的轮次，两者口径有意明确区分。

## 检查点与 Git 的边界

当前实现有两类独立内容：

- `ContextCheckpoint`：验证原始历史指纹后复用压缩缓存，避免重复压缩；前端查看历次缓存。
- `Checkpoints`：在步骤结束、运行结束及人工同步时，将 ShortMemory、来源摘要 seq、任务身份和覆盖日志 seq 追加为不可变快照。

同步方向是 **当前状态 → 新检查点**。它不会把旧快照覆盖到当前任务，也不会恢复项目文件、回滚 Git 或重启在途请求。自动断点续跑仍需要额外设计：恢复游标、未决工具处理、幂等约束、工作区版本校验及明确的恢复授权。项目文件历史版本继续用 Git。

## 模块组织

- `backend/observability/`：关联上下文、请求输入、请求生命周期、只读轨迹投影。
- `backend/short_memory/checkpoints.py`：任务状态快照。
- `backend/evaluation/`：规则模型、版本存储、纯离线判分。
- `backend/api/diagnostics.py` 与 `evaluations.py`：各自的接口入口。
- `frontend/inspection/`：日志、检查点、状态和记忆各自一个模块，主入口负责协调。
- `frontend/evaluation/app.js`：独立评测页面。

继续使用现有 JSONL journal 与 JSON 原子写入，不引入新数据库、前端框架或评测 Agent。扩展 trace 不再要求调用方到处手动拼装关联字段；真实 Provider 才决定发送的参数，不维护第二套近似请求。

## 面试里的个人思考

值得讲的不是“加了日志、加了页面”，而是以下几个可验证的取舍：

1. **观测属于运行协议。** 请求重试是多个尝试，而不是在一条开始记录上改次数；后台任务必须保留来源身份。通过取消、断流和跨轮并发来检验协议，比只展示成功任务更有说服力。
2. **上下文是运行输入的一部分。** 保存消息历史还不能复现实验，因为摘要和指令改变了实际请求。记录有效输入与内容版本，才能研究压缩是否减少成本、是否牺牲任务质量。
3. **人工状态与执行证据分开。** 允许用户编辑状态、同步快照，同时不允许一个“完成”标记篡改测试结果。可管理性和事实可靠性可以同时成立。
4. **先建立廉价、可复核的评测闭环。** 用已有会话验证规则，不额外消耗模型；同时坦承它不是隐藏测试成功率。下一步可以在相同 trace 协议上加入隔离执行验收，避免推倒重做。

证据比功能数量更能体现技术深度：展示一次已完成但未验证的任务、一次断流、一个跨轮后台请求、一个人工修改与自动状态更新的冲突，以及对应的不变历史报告。
