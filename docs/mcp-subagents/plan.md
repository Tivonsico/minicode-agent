# MCP 与只读子智能体实施计划

日期：2026-10-18。状态：规划草案，尚未开始实现。

用户已确认：第一版子智能体只读分析和审查，由主智能体统一改文件。其余范围和数值是本文建议的实施默认值，不表示用户已经逐项确认。

## 目标与使用方式

用户可以配置 MCP 服务并选择开放哪些工具。主智能体通过现有工具接口调用它们，也可以把边界明确的分析任务交给子智能体。用户在当前聊天里查看进度、结果和消耗，停止当前任务会停止全部子任务。

例如主智能体处理一个缺陷时，派一个子智能体查找相关调用方，派另一个审查异常处理。它自己继续读代码，汇总结果后修改文件并验证。子任务结果应包含发现、文件位置、依据及未解决问题。

第一版提供一层委派。子智能体不修改文件、不运行 Shell、不继续创建子智能体。先使用与主智能体相同的模型配置，独立选模型留到后续。MCP 首版聚焦工具发现与调用；内置服务市场、完整 OAuth 登录、MCP resources/prompts 浏览和多模态结果展示后续再做。需要这些能力的服务应明确显示暂不支持。

现有文件工具、审批、模式、沙箱及历史恢复行为构成回归基线。无需改成每种工具一个子类。

## 方案一：统一工具入口

工具仍然由名称、描述、参数 Schema 和 handler 构成。工具来源区分 builtin、mcp、subagent。新增策略信息用于表达可见范围、资源访问、是否允许并发和是否需要确认，不让一个 read_only 字段承担所有判断。

每轮开始生成工具集合快照。模型只能看到当前模式和权限允许的工具，执行前再次检查授权。工具执行采用同一条路径：查找、参数校验、权限检查、必要确认、调用 handler、结果归一化及记录。

MCP 的服务 ID 使用本地配置中的稳定标识；工具别名建议为 `mcp__<server_id>__<tool_alias>`。为模型接口处理字符和长度限制，必要时加短哈希，并保留原名的反向映射。服务重名、工具重名均不能覆盖内置工具。

第一阶段只做必要抽取，不重写整个工具系统。原有本地处理函数继续复用，避免同一调用出现两次审批。

## 方案二：MCP 接入

建议新增 `backend/mcp/`：

- `config.py`：服务地址或启动参数、凭据引用、允许工具及限制。
- `manager.py`：创建和关闭客户端、发现工具、维护可用状态。
- `adapter.py`：把 MCP 工具包装成现有 Tool；调用后转换为 ToolResult。
- `process.py`：本地 stdio 进程的启动、隔离、标准流及退出管理。

协议编解码、版本兼容由官方 Python SDK承担，实施时锁定实际验证过的 SDK 与服务版本，不手写 JSON-RPC。标准传输包括本地 stdio 与远程 Streamable HTTP；先用一个可控的只读 HTTP 服务完成端到端验证，再加入受限 stdio 启动器。[官方传输说明](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports)、[官方 Python SDK](https://github.com/modelcontextprotocol/python-sdk)

客户端通过 `tools/list` 获取工具，通过 `tools/call` 调用。发现过程处理分页；收到工具列表变化时，标记当前快照需要刷新。服务掉线可重新建立连接，但不能自动重放已经发出的修改操作。[MCP 工具规范](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)

授权采用应用自己的设置。服务提供的只读标记可以辅助展示，不能独自决定权限或并发安全；规范也要求谨慎对待工具 annotations。[规范中的 annotations 要求](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#tool)

具体行为建议如下：

- 服务由用户配置和启用。只连接服务不等于开放它的全部工具；每轮仅注册选中的工具，并限制总 Schema 大小。
- 主智能体调用已开放的普通查询工具按设置执行。未知副作用工具默认不自动执行；外部修改操作仍需明确授权。plan 模式与只读子智能体只能获得经本地设置认可的只读能力。
- 远程 MCP 单独配置可访问端点和凭据，不依赖 Shell 的联网权限。现有 Shell 继续禁网。远程服务如何访问数据由服务自身的账号权限约束，本地目录检查不能替它作保证。
- stdio 服务必须走专用受限启动器，限制工作目录、继承环境和网络；验证现有隔离设施能否在双向标准流下工作。无法满足隔离要求时将该服务标为不可用，不直接无隔离启动项目内命令。
- 凭据只留在后端，并扩展日志脱敏范围；凭据、完整环境变量和启动错误中的秘密不能送给模型或前端。
- 正常工具错误、协议错误、超时分别返回。外部修改请求发出后若无法确认结果，记录 unknown，不把取消或超时当作操作未发生。
- 第一版向模型返回文本和结构化 JSON，保留原始结果类型信息。图片、音频等结果只给出受控的描述或附件提示，不把二进制直接塞进聊天上下文。
- 工具列表变更不在一轮中悄悄替换执行目标；服务身份、工具定义或授权版本变化时，拒绝旧调用并要求刷新。

## 方案三：只读子智能体

建议新增 `backend/subagents/`，包含任务管理、上下文组装、能力配置和结果模型。复用 AgentLoop、Provider、上下文预算和日志接口；每个子任务拥有自己的循环实例、执行器、读文件记录和上下文，不能复用主智能体的可变会话对象。

主智能体新增三个工具：

| 工具 | 输入与返回 | 作用 |
|---|---|---|
| `SpawnAgent` | 目标、必要背景、读取范围、返回要求；返回任务 ID | 提交后台子任务，快速返回，主智能体可继续工作 |
| `WaitAgents` | 当前轮次拥有的任务 ID、有限等待时长；返回状态和新增结果 | 等待结果或查看进度，返回游标避免重复结果 |
| `CancelAgent` | 当前轮次拥有的任务 ID；返回停止状态 | 停止不再需要的任务 |

这些名称为建议，实施时可统一命名。状态查询和等待共用 WaitAgents，第一版不增加跨任务自由发消息和无限轮续聊。

上下文由任务目标、主智能体选择的必要背景、相关项目规则、允许读取的目录和工具组成。独立读取需要的文件，不复制整个主聊天。结果通过结论、证据、未完成项和状态返回主智能体；不自动写入长期记忆，也不把子任务发来的文字当作用户新授权。

子智能体拥有 ReadFile、Glob、Grep，可按任务需要加载技能和读取技能资源。技能不能增加工具权限。经本地设置审核的只读 MCP 工具可按任务单独分配；第一阶段也可先不向子智能体开放 MCP。

目录和 MCP 能力只能是主任务授权的子集。权限撤销在调用前即时生效，不能只在创建时复制一份永久授权。创建任务后固定模式和任务范围，子智能体不能把任务升级到 auto 模式。

子任务结果引用的文件应记录读取时的版本。主智能体使用结果前检查相关文件是否已改变；改变后标记结果过期，重新读取或重跑相关子任务。第一版不承诺多文件原子快照。主智能体开始依赖这些分析的修改前，先收齐相关子任务结果。

## 生命周期、并发与消耗

首版建议：每轮最多创建 4 个子任务，同时最多运行 2 个，委派深度为 1。每个子任务最多 8 次模型请求、运行 180 秒；主任务与子任务共享现有的本轮 30 次模型请求总额度。以上均为可调整的初始值。

预算必须在真正发请求前原子预留，重试和本轮上下文压缩请求也要计入，避免并发任务各自检查后一起超额。日志显示主任务和各子任务用量，并避免汇总两次。长期记忆后台提取按现有独立生命周期统计。

SpawnAgent 只启动任务并返回 ID。WaitAgents 等待时不能持有会阻止子任务读取或完成的资源锁，也不能让子任务重新进入主执行器。控制操作和文件读写操作使用不同调度规则。

任务状态包含 queued、running、completed、failed、cancelled、interrupted；工具调用另可保留 unknown。停止主任务时停止排队及运行中的子任务，关闭其外部调用。停止单个子任务不停止其他任务。主任务最终回复前应收齐结果或显式取消未完成任务，避免后台孤儿任务。

子任务日志建议放在父会话目录下的独立子目录，保存 parent_run_id、agent_id 等关联。它们不出现在用户普通聊天列表中；详情接口检查父会话与任务归属。复用日志协议需要适配存储路径，不能直接新建普通 RuntimeSession 后混入聊天列表。

浏览器刷新只重新观察状态。后端重启把未完成子任务标为 interrupted，保留已完成结果；不自动重跑 MCP 调用或子任务。

## 分阶段实施与验收

| 阶段 | 工作 | 完成条件 |
|---|---|---|
| P1 工具入口与权限 | 工具来源、动态注册、运行快照、调度类别和统一权限入口 | 原九个工具行为保持；非法参数、重名和未知工具仍被拒绝；动态工具可受模式过滤 |
| P2 MCP 最小链路 | HTTP 客户端、工具发现、适配、后端配置和错误处理 | 可控服务从列举到实际调用通过；分页、名称冲突、掉线、超时、错误结果和秘密脱敏通过 |
| P3 MCP 本地服务与设置 | 受限 stdio 启动器、工具开关及连接状态页面 | 本地示例服务可调用；退出清理子进程；越界和禁网探针有效；未隔离服务不可用 |
| P4 子任务最小链路 | 管理器、独立上下文、Spawn/Wait/Cancel、共享预算和只读能力 | 两个子任务可并行分析；彼此日志和历史独立；不能写文件、运行 Shell 或继续委派 |
| P5 停止、恢复和页面 | 当前聊天展示子任务状态、结果、用量；级联取消与重启恢复 | 刷新不丢状态；停止无孤儿；重启标记中断且不重放调用；子任务不可越权读取其他任务结果 |
| P6 联合验收 | 主任务使用 MCP，并派子任务分析后汇总 | 主智能体拿到可引用结果；未授权 MCP 工具不可调用；总预算准确；原有模式、文件权限和审批检查通过 |

P2 到 P3 完成后可以单独交付 MCP。P4 到 P5 完成后可以交付只读子智能体。两条能力通过同一工具入口组合，任意一条未启用时，另一条仍可使用。

测试优先覆盖真实边界：并发抢占最后一次请求额度；等待期间取消；权限撤销；外部操作超时状态不明；文件在子任务读取后被主任务修改；后台任务崩溃；审批后服务工具定义发生变化。先用确定性的假 Provider、可控 MCP 服务测试，再做用户配置服务与真实模型的冒烟验收。

## 后续扩展

等只读协作稳定后，再考虑独立模型配置、子任务追加消息，以及可写子智能体。可写协作需要另行设计工作区隔离、修改合并和冲突处理，不能仅移除只读限制。
