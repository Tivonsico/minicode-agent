# 重启后 MySQL 会话占用修复

## 故障与恢复

2026-10-20，打开已完成的会话返回 HTTP 409，提示“会话仍被执行者占用”。当时仅有当前项目后端在运行，旧后端进程已退出，但数据库中的会话 owner 未被释放。

核查时，该会话已完成、未被当前后端接管，没有 STARTED/UNKNOWN 工具操作，也没有工作区占用。确认旧执行者停止后，通过既有的 `owner/reconcile` 接口提交核查证据解除遗留占用；未删除会话、历史消息、检查点或工具记录。

## 原因与修复

`start.py` 重新启动前调用 `backend.runtime.process.stop()`。旧实现直接强制杀死后端及子进程，绕过 Uvicorn lifespan 和 `RuntimeService.close()`，从而跳过 MySQL 会话 owner 的释放。下一后端无法区分该占用是否仍活跃，按原有保护规则拒绝打开。

macOS/Linux 现在先向经过 PID、创建时间和项目锁校验的旧后端发送 SIGINT，最多等待 8 秒，让后端取消并等待任务、保存状态并释放数据库会话。等待时追踪已观察到的子进程；超时后仍强制结束残留进程。僵尸进程视为已退出，避免非父进程的停止脚本无谓等待。

Windows 暂保留原有强制停止方式。强退或写入结果不确定时，数据库 owner、未知操作和工作区占用仍按原有协议核实，不自动清空。任意脱离父进程并自行后台运行的脚本不属于新增的进程监管能力；正常后端关闭依靠现有工具与快照模块等待其管理的子进程完成。

## 存储配置保存修复

恢复后复查发现，当前配置已切换到本地模式。此时只要打开过本地会话，再保存存储配置，后端就会访问本地 `SessionStore` 不存在的 `owner` 属性并报错，影响切换回 MySQL。现在仅在运行中的存储为 MySQL 时收集会话 owner；本地模式传入空集合，仍执行原有未核实操作检查。

新增回归分别覆盖已有本地会话时保存本地配置，以及实际连接独立 MySQL 后保存从本地切换到 MySQL 的配置。保持原有“保存后重启生效”的行为，不迁移两种模式的历史，也不替用户更改当前模式选择。

## 验证

- 实际 API：故障会话先稳定返回 409，恢复后返回 200，原有历史保留。
- 进程回归：正常关闭能够执行持久资源清理；忽略 SIGINT 的进程在等待超时后被结束；继续验证旧 PID、无关进程和子进程清理。
- 真实 MySQL：独立测试实例中创建持有 owner 的后端子进程，通过停止脚本关闭后，新后端可重新获取同一会话。将测试进程内的停止函数换成旧实现时，可复现完全相同的占用异常。
- 最终配置独立 MySQL 实例运行完整测试：`307 passed`，无跳过项；静态检查通过。此前一次评测矩阵用例触发其 3 秒等待上限，最终完整复跑通过，未放宽断言或修改该用例。
- 使用修复后的标准启动脚本重启正式本地服务，保留当时配置的存储模式，并检查现有会话可以打开。
- 最后核查时，本地模式 4 个会话均返回 200；MySQL 中 4 个历史会话保留，遗留 owner 数量为 0。

测试使用独立数据库和临时项目；未在用户会话中发送模型任务，也未绕过未知副作用的保护规则。
