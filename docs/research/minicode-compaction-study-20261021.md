# Minicode 的上下文成本与压缩保真：现有证据和实验建议

核查日期：2026-10-21。本文基于当前工作区源码和本地已有轨迹；没有修改运行机制、发起收费模型调用或执行新的长任务。工作区存在此前未提交改动，当前源码不能自动代表旧轨迹生成时的实现。

建议先用 Minicode 做主实验，用 DeepSeek 官方实现帮助选择策略。先完成已有轨迹的成本画像，再做同一历史切点上的压缩对照，最后用少量端到端运行验证。这样每一步都有独立能回答的问题。

## 本地数据到底支持什么

离线扫描 `.minicode/sessions/*/session.jsonl` 和 `.minicode/swe-bench/jobs/**/trace.json`，共 47 个文件。原始有 1,057 条 request_start；其中 48 条属于重复导出的请求，按 session_id/request_id 去重后是 1,009 次：主请求 1,002 次、memory 7 次，9 次用量未知，1 次缺输入引用。扫描范围不含 MySQL 中可能存在但未导出的会话，也没有把任意测试产物都当成真实运行。

所有扫描文件中，context_compressed、context_compression_error、context_overflow 都为 0，也没有 compression 请求。这些样本可用于成本画像；它们没有提供实际压缩后的事实一致性证据。不能从“有 80% 触发代码”推断已经测过长期保真。

为避免混合开发重跑版本，主要成本分析选已有冻结首轮 25 题。来源是 [首轮报告](../harness/swe-bench-25-first-results.md) 和同名 JSON。该组 596 次请求，593 次有实际 usage，核算结果与原报告一致：累计输入 5,731,003 token，输出 126,417 token；总量 5,857,420。另有 3 次未知消耗，因此不是完整费用账单。

从实际保存的请求 payload 逐项统计 JSON UTF-8 字节，并在每次发送时重复计数：

| 输入部分 | 累计字节占比 |
| --- | ---: |
| 工具结果消息 | 37.1% |
| assistant 历史（含工具参数、reasoning_content） | 31.2% |
| system/developer 消息 | 13.5% |
| 工具定义 | 9.1% |
| user 消息 | 9.1% |

字节占比不是 tokenizer 的 token 占比，也不是浪费率。统计包括各条消息的协议字段，不包括 payload 最外层封装；assistant 字段的进一步拆分只计算字段值，不与上表重复相加。实际模型 tokenizer 对中英文、代码和 JSON 的编码不同，当前数据不支持精确宣称“37.1% 的 token 花在工具结果上”。

工具结果的累计字节中，ReadFile 占 59.4%。assistant 历史中的 reasoning_content 字段值约 398 万字节，约为上述累计输入组件字节的 16.3%。说明需要同时检查代码读取、旧推理和工具参数的反复携带。是否能省，必须结合后续动作判断；特别是推理字段可能受 provider 的工具调用协议约束，不能直接删掉后称为等价优化。

已知输入中有 3,946,944 cached_tokens，约占已知 prompt_tokens 的 68.9%。这是输入的子集，不额外加进总 token。输出中的 reasoning_tokens 也是 completion_tokens 的子集。减少历史可能改变缓存命中，因此总 token、费用、耗时要分别看。

数据和每份轨迹的 SHA-256 保存于 [画像 JSON](minicode-context-costs-20261021.json)。可复算脚本为 [profile_context_costs.py](../../others/harness/profile_context_costs.py)，只读取已有轨迹并更新画像文件，不调用模型。

## 源码里的实际压缩语义

- [budget.py](../../backend/context/budget.py)：估算以 JSON UTF-8 字节数加常量计算，注释明确不是计费 token。输入预算取 context_window 减输出预留，并受 model_max_input 限制。
- [builder.py](../../backend/context/builder.py)：估算达到输入预算的 80% 才尝试压缩；按消息组保留最近四组及最新 user，其余历史交给摘要。assistant 工具调用和对应结果保持同组。因此把关键约束只写进最新用户消息，会绕过所要研究的遗忘问题。
- [compactor.py](../../backend/context/compactor.py)：当前使用自由文本摘要，提示保存约束、决定、未完成工作、路径与引用，禁止虚构完成。超长输入可拆多个摘要调用，其结果拼接；这部分成本也要计入实验。
- [compaction_cache.py](../../backend/context/compaction_cache.py)：原历史指纹验证后复用摘要缓存，保护的是来源一致性。

当前摘要接纳条件检查预算下降、候选不超窗、工具调用配对完整。它没有逐事实的语义正确性验收。“来源指纹正确”和“工具协议合法”不能证明摘要没有漏掉用户约束。

长工具结果外置和 Skill 按需读取已经存在，分别见 [OutputStore](../../backend/storage/output_store.py)、[提示组装](../../backend/context/prompts.py) 和 [SkillCatalog](../../backend/skills/catalog.py)。因此下一步应研究预览长度、历史重复、加载正文何时退出上下文等具体变量，不能把“首次加入外置/按需加载”写成已有问题的答案。

## 优先检验的假设

一个早期工具结果若一直保留，会随每次后续请求再次发送。其累计负担取决于大小与存活请求数，而不只取决于输出时有多长。重复携带本身也不等于无用：有些事实正是靠它维持。

先检查首轮中的 pytest-dev__pytest-11148：30 请求，564,172 已知累计 token，最终 unresolved，有 8 次 ReadFile、11 次 Shell、8 次写入/编辑，适合检查读取、修改、验证之间的历史增长。再看成功样本 pylint-dev__pylint-7114：30 请求、367,821 已知累计 token，官方 resolved，避免只从失败任务推出结论。最高输入消耗的 pylint-dev__pylint-7080 有 21 次 Shell、最终 empty_patch/RequestLimit，需单独排查执行循环和环境反馈，不能把请求多全部归因于记忆。

离线裁短已有 payload 只能估计潜在输入减少量。要知道模型是否找回信息、重读多少次、最终是否成功，必须重新续跑。

## 最适合的第一条长任务

选一个预先准备好的小型 Python 任务清单 CLI 项目，做 JSON v1 → v2 存储升级。项目有现成测试、固定依赖和跨文件模块，运行不需要联网。不要第一轮就让 agent 从零写整个项目；先确认完整历史组能通过，再用它研究压缩。

任务沿同一 session 分阶段推进，每阶段一轮输入，累计约 40–60 次主请求作为试跑目标，而不是硬性长度。重点是跨过一次压缩并在之后仍需要早期事实。Minicode 每轮最多 30 次请求，实验还需设跨轮统一总请求/时间预算，防止某组靠更多“继续”获得优势。

| 阶段 | 让 agent 做什么 | 后续需要保留什么 |
| --- | --- | --- |
| 1 | 阅读旧 CLI、存储代码和现有测试，记录兼容约定 | 旧命令和退出码、未知字段、ID 语义 |
| 2 | 按用户纠正后的方案实现迁移与兼容读取 | 最新决定覆盖旧决定；已做与待做不能混写 |
| 3 | 跑目标测试、定位失败，再检查正常规模的旧数据样例 | 哪个测试失败、改了哪些文件、样例中部的边界 |
| 4 | 在约束所在历史已进入摘要后，要求完成 dry-run 和最终验收 | 早期约束在实际代码中生效，最终验证覆盖最后修改 |

初版放 8–12 条可检验事实即可，例如：

1. 保留 `list --json` 旧输出字段。
2. ID 始终为字符串，`"0012"` 不可变为整数。
3. 旧数据的未知字段迁移后保留。
4. 无效 JSON 保持退出码 2。
5. `--dry-run` 不改变数据文件字节与 mtime。
6. 不引入第三方依赖。
7. 早期决定原地覆盖，后续用户明确改为先备份再原子替换；最终必须遵守后者。
8. 混合新旧格式的输入必须报错，不能“尽力迁移”后声称成功。
9. 一个跨文件测试早期失败，直到后段才修复；摘要不得把它写成已通过。
10. 末次代码修改后必须再验证；旧的绿色测试不代表当前文件状态。

这些是拟议任务约定，不是本项目当前功能。每条约定都要配独立断言或运行事件检查。文件状态用文件哈希、补丁和验证时序核对；不要考模型能否背出早已失效的行号。

约束在早期对话自然给出，后段只说“完成剩余迁移并验收”，不重贴完整约束清单。否则最新用户消息直接保留答案，测不到压缩。隐藏验收器与事实清单不得进入 agent 可读目录；若所有事实都写进始终可读的 README，应明确是在测信息找回成本。可分别标记“只在对话出现”和“可从代码/文件恢复”的事实。

首轮先排除工具中断、数据库恢复、多 agent 并发，以免失败原因混在一起。待压缩主线跑通，再增加受控外部文件修改，且各策略必须从同一修改后工作区继续。

## 对照怎么跑

先做一个任务、三种策略、各三次，共 9 次续跑，确认任务和判分器可用；再扩成三个任务变体，共 27 次。这只是筛查规模。

在同一条历史的压缩切点保存：完整消息、工具定义、模式、模型与参数、工作区快照、剩余预算、记忆快照。然后从同一状态续跑：

| 组 | 历史处理 |
| --- | --- |
| A | 完整历史，关闭该切点压缩 |
| B | 当前自由文本摘要，保留最近四个消息组和最新 user |
| C | 相同摘要模型/预算及尾部保留规则，但摘要按有效约束、当前决定、已验证文件状态、未完成工作组织；事实带来源引用，显式标记被撤回决定 |

A 的完整历史必须能放进同一真实模型窗口。第一轮可以在模型尚能容纳完整历史时手动触发一次压缩，这测的是受控切点保真；不能叫生产默认阈值的自然触发效果。若通过降低估算输入预算制造压力，所有组的真实模型窗口仍需相同，并明确 A 的压缩开关是实验干预。单独补默认配置的自然触发运行，报告实际触发率。

同一切点上的分支可以隔离已有过去，比较改变摘要后的后果。摘要生成与续跑都有随机性，应记录每次实际摘要；多个切点来自同一任务时不能当成完全独立任务扩充样本。端到端实验再从头独立运行，观察策略改变读取和工具选择后能否维持收益。

B/C 的摘要输出预算保持一致，否则无法区分事实组织与更长摘要的效果。新 session、隔离工作区、同一初始长期记忆，禁止前一组的记忆泄漏到后一组。初版不同时修改 Skill、输出外置和摘要阈值。后续才加一组“旧工具结果裁剪 + C”，用于测额外收益。

## 最后应该报哪些数

- 全任务 token：主请求 + 压缩 + memory/其他辅助 + 重试，输入输出分列；未知量另列。切点实验的共同前缀成本单列，不能只比较摘要后的首个请求。
- 缓存和费用：cached/uncached 输入分别记录，用同一已核验价格计算费用；没有价格就只报告 usage，不伪造费用。
- 事实保真：切点上仍有效且未来相关的事实，摘要正确保留多少；过时决定是否错误复活；假完成和错误文件状态分别计数。改写同义表达要人工复核，不能只用关键词命中。
- 行为与成功：约束是否实际被遵守，独立隐藏测试通过率、所有关键约束同时通过率，事实找回的额外读取次数/token，任务耗时。

错误链按“原始证据 → 摘要 → 实际下一次请求 → 行为 → 验收”回溯。摘要漏事实但重读找回，是保真失败后的成功恢复；摘要保留事实但模型仍违约，是后续执行失败。两种情况不能混成一个遗忘率。

小样本报告“这批任务 token 变化 X、通过数 a/n→b/n、哪些事实出错”，不要把没有显著差异写成“证明同等通过率”。正式非劣效比较需要预先确定容许通过率差与样本量。可以先画 token 与关键约束通过率的取舍曲线，找出值得扩样的策略。

## DeepSeek 的位置

这里暂按官方 [deepseek-ai/deepseek-harness](https://github.com/deepseek-ai/deepseek-harness) 理解。其 [压缩配置](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/compaction/compaction-basic/src/config.ts) 也有 0.8 默认阈值；[工具结果裁剪](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/compaction/compaction-tool-result-pruner/README.md) 和 [token-meter](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/llm/token-meter/README.md) 值得借鉴。详见 [一手资料笔记](../harness/deepseek-research-notes.md)，远端 master 本次未锁 SHA。

换整套运行系统会同时改变提示、工具、预算和检索行为，无法只归因到压缩。Minicode 内的策略对照完成后，再抽同一组任务到 DeepSeek 上验证可迁移性。面试时能讲清自己系统里的实际测量、失败案例和取舍，比同时搭两套评测更有价值。
